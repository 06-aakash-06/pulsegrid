# Runtime stability, O-01 and Tempo

All timing and trace identifiers below are from sanitized local logs. The original consultation request returned 504 at `2026-10-25T08:17:11.235701Z` after 5,717.265 ms. Request `6e08ceaf-d3ec-457a-af3c-ed4e12fe1260`, correlation `e4b34845-95b3-40a8-a494-7e3bb4f06e41`, trace `2ed408928748c17e9ec2109b12136596`. Traefik did not originate the timeout. The Records client exhausted its five-second request budget while the downstream clinical-hold command committed successfully with 200 in 1,203 ms (client span 1,413 ms). Appointment/Records authority calls included a 344 ms Patient status lookup; others were 12–44 ms. Stable-key/idempotent recovery returned the stored outcome. Pools were 3+2 connections, SQL/lock budgets 2s/1s, and no blocked transaction was present when inspected. Historical Appointment CPU throttling is not causal proof. A client-construction probe was usually 4 ms, with isolated 54/98 ms samples, not enough evidence for a client lifecycle rewrite. Exact sanitized request/trace chains are in [original failures](evidence/original-failures.json) and [trace evidence](evidence/original-traces.json).

The original Surge GET returned 503 at `2026-10-25T08:29:19.463312Z` after 102.807 ms. Request `184e1bd2-6818-49b2-9a33-af8f6eaa21a`, correlation `184e1bd2-6818-49b2-9a33-af8f6eaa21a5`, trace `749a518a721cae103c4d848ecb294393`. Redis `EVALSHA` timed out reading after 68.509 ms. The first, incomplete Phase 10 helper observed one additional isolated Surge 503 but saved only its status, not request/trace IDs. That status is retained as a reproduction signal, not root-cause evidence. A corrected read-only probe made eight requests over 109.2 seconds: all eight returned `NORMAL`/200 in 56.7–357.2 ms, and all eight associated traces were queryable. Its per-request IDs are in [Surge reproduction evidence](evidence/surge-status-reproduction.json). This bounded non-reproduction does not prove the intermittent failure eliminated; O-01 remains unresolved.

Tempo is pinned to `grafana/tempo:3.1.0`, with the existing 512 MiB and 0.25 CPU limits. The prior baseline sampled 31 probes over 624.9 seconds: readiness and search 200 throughout, RSS 159.9–244.4 MB, restart count 4, `OOMKilled=false` at inspection. The four restarts are historical; current `OOMKilled=false` does not establish their cause. Before the guard, effective defaults allowed 20 concurrent queries, 1,000 search jobs, 400 storage workers and a 20,000-job queue, with automatic memory limiting disabled; see [pre-change effective config](evidence/tempo-effective-config-before.yml).

The focused configuration change enables Tempo's existing automatic memory limit at ratio 0.8 (409.6 MiB soft target within the unchanged 512 MiB container limit), caps concurrent queries at 2 and search jobs at 4, and bounds local-storage workers/queue at 8/64. WAL path, local storage, and 24-hour local-block retention are unchanged. [The post-change `/status/config`](evidence/tempo-effective-config-after.yml) confirms the effective values in the isolated stack. This is a resource-pressure guard, not proof that it caused or eliminates historical restarts. Tempo's pinned image has no shell or HTTP client, so no in-container readiness healthcheck was added; readiness was queried from the adjacent service network.

The corrected same-stack observation ran for 600.97 seconds with 21 samples. It sent one authenticated synthetic Patient `GET /api/v1/doctors?limit=5` through the isolated gateway per sample, then queried that same request's trace in the Tempo instance receiving it. Readiness 21/21, metrics 21/21, fixed Doctor search 21/21, API reads 21/21 HTTP 200, and previous-request trace fetches 20/20 HTTP 200. The span-received counter increased from 65,193 to 87,071. RSS ranged 157.2–309.0 MB (30.7%–60.3% of 512 MiB); the effective Go soft limit was 429,496,729 bytes. Restart count began and ended at 0; the container remained running with `OOMKilled=false`. The restarted container's count cannot be compared continuously with the old count of 4. This ten-minute healthy interval does not prove indefinite stability.

The monitor recorded 15 scheduler warnings and 15 corresponding scheduler errors containing `NotFound: no jobs found`; 7 additional rate-limited `attributes truncated` warnings appeared. The `no jobs found` idle-poll behavior matches the pinned [Tempo v3.1.0 backend worker](https://github.com/grafana/tempo/blob/v3.1.0/modules/backendworker/backendworker.go) and [upstream issue 7403](https://github.com/grafana/tempo/issues/7403). These messages do not explain the four historical restarts; no other Tempo warning/error class was observed during the window. Full samples and counters are in [the completed observation](evidence/tempo-observation-after.json).

OpenTelemetry did lose spans during destination unavailability. A bounded 1,000-line retained Collector log tail contained 99 `Exporting failed. Dropping data` events totaling 5,770 spans across `2026-10-24T17:43`–`17:46Z` and `2026-10-25T09:11Z`. The 09:11 bucket alone was 20 events/928 spans during the planned retained Tempo recreation; earlier events align with unavailability windows but are not all attributable to a particular restart from preserved evidence. A bounded isolated Collector tail contained 8 events/453 spans while Tempo was starting at 09:08:28–09:08:33Z. After readiness, the corrected observation retrieved 20/20 synthetic request traces successfully. See [Collector drop summary](evidence/otel-export-drops.json). Hospital requests remained independent of the optional exporter. Collector queue durability/startup ordering remains an operational limitation; this work did not add another service or claim telemetry survives a Tempo outage.
